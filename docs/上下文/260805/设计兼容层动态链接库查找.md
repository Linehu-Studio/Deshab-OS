# SYSTEM/lib/ 统一动态库搜索路径实施计划

## 总体架构概述

本计划涉及三个兼容层集成目标：(1) FAT32 LFN 长文件名解析，(2) PE 真实 DLL 加载，(3) Linux 启动时 .so 推送。这三者有明确的依赖链：LFN 是基础（库文件有长名如 `libstd-6g.so`），PE DLL 加载和 Linux .so 推送都依赖 LFN 才能从 SYSTEM/lib/ 读出文件。

---

## Part 1: LFN 长文件名支持

### 1.1 设计决策：共享头文件方案

创建 `CODE/tools/fat32_lfn.h` 作为 static inline 共享库，与现有 `fat32_io.h` 同模式。理由：

- 三个 FAT32 实现位置（UTSM dsk_loader.c、DSK main.c、tools/fat32_io.h）各有独立缓冲区和 block I/O 接口，无法抽取为单一共享实现
- LFN 解析逻辑是纯算法，无状态依赖，适合 static inline 函数
- 各调用点在遍历目录项时调用 LFN 收集函数，收集结果与短条目匹配

### 1.2 LFN 数据结构与核心算法

**LFN 目录项布局**（attr=0x0F）:
```
偏移  大小  含义
0     1     序号（bit6=最后一片段, bit5=0x40）
1-10  10    name1 (5 个 UTF-16 LE 字符)
11    1     attr (0x0F)
12    1     type (0)
13    1     checksum
14-25  12   name2 (6 个 UTF-16 LE 字符)
26    2     首簇号 (必须为 0)
28-31  4    name3 (2 个 UTF-16 LE 字符)
```
每个 LFN 项携带 13 个 UTF-16 LE 字符。多项按**逆序**存储（最高序号最先出现），紧接其后的短名项是此 LFN 链所对应的 8.3 条目。

**fat32_lfn.h 核心接口**:

```c
// LFN 最大长度（FAT32 规范最多 20 个 LFN 项 = 260 字符）
#define FAT32_LFN_MAX 256

// LFN 收集缓冲（栈分配即可，调用方局部变量）
typedef struct {
    u16 chars[FAT32_LFN_MAX];  // UTF-16 LE 累积字符
    int  count;                 // 已收集字符数
    int  seq_expected;          // 期望的下一个序号（逆序收集用）
    u8   checksum;              // 校验和（来自首个 LFN 项）
    int  valid;                 // 1=LFN 链完整有效
} fat32_lfn_buf;

// 初始化 LFN 缓冲
static inline void fat32_lfn_init(fat32_lfn_buf *buf);

// 处理一个目录项：如果 attr==0x0F，收集 LFN 片段；
// 如果是短名项，校验 checksum 并确认匹配。
// 返回：1=此短名项有完整 LFN，0=无 LFN 或 LFN 不完整
static inline int fat32_lfn_process(fat32_lfn_buf *buf,
                                     const void *entry32,  // 32 字节目录项
                                     int is_lfn_entry);    // attr==0x0F ?

// 从 LFN 缓冲提取 ASCII 名（UTF-16→ASCII 缩窄，仅处理 BMP U+0000..U+007F）
// 返回 NUL 结尾 ASCII 字符串长度，-1 表示含非 ASCII 字符
static inline int fat32_lfn_to_ascii(const fat32_lfn_buf *buf,
                                      char *out, int out_cap);

// 计算 8.3 短名的 LFN checksum
static inline u8 fat32_lfn_checksum(const char name11[11]);

// 用长名或 8.3 短名匹配目标
// 返回：1 匹配（LFN 优先），0 不匹配
static inline int fat32_lfn_match(const fat32_lfn_buf *buf,
                                   const char name11[11],
                                   const char *target_long,  // ASCII 长名（可为 NULL）
                                   const char *target83);    // 8.3 短名（可为 NULL）
```

**LFN 收集算法**（`fat32_lfn_process`）:

1. 如果 `is_lfn_entry`：读取序号 `seq = entry[0] & 0x3F`
   - 如果 `entry[0] & 0x40`：这是最后一个 LFN 片段（逻辑上最前面的），设置 `buf->seq_expected = seq`，`buf->count = 0`
   - 从 entry 偏移 1-10/14-25/28-31 提取 13 个 UTF-16 LE 字符
   - 将字符写入 `buf->chars[(seq-1)*13 .. seq*13-1]`（逆序存储但正序放置）
   - 保存 `buf->checksum = entry[13]`
   - 清除 `buf->valid`（等短名项校验）
2. 如果是短名项：
   - 计算 `name11` 的 checksum，与 `buf->checksum` 比较
   - 匹配则设 `buf->valid = 1`
   - 不匹配则 `buf->valid = 0`，清空缓冲

**关键约束**：LFN 收集在目录遍历循环中进行——每当遇到 `attr==0x0F` 的条目，调用 `fat32_lfn_process` 收集；遇到短名条目时，`fat32_lfn_process` 做校验收尾。这意味着每个调用点（`fat32_find_in_dir` 等）的遍历循环需要改造，不再 `continue` 跳过 `attr==0x0F`，而是传入 LFN 收集器。

### 2.2 DLL 缓存与导出表解析

**缓存结构**：
```c
#define PE_DLL_CACHE_MAX 32

typedef struct {
    char name[64];        // DLL 文件名（小写，如 "user32.dll"）
    u64  image_base;      // pe_load_image 返回的基址
    u64  image_size;      // SizeOfImage
    u32  export_dir_rva;  // 导出表 RVA（0=无导出）
    u32  export_dir_size;
    int  is_pe32_plus;    // 影响地址宽度
    int  load_ok;
} pe_dll_entry;

static pe_dll_entry g_dll_cache[PE_DLL_CACHE_MAX];
static int g_dll_count;
static pe_dll_reader_fn g_dll_reader;
```

**导出表解析算法**（`pe_dll_resolve`）:

```
IMAGE_EXPORT_DIRECTORY 结构（位于 DLL image 的 export_dir_rva 处）:
  +0x00 Characteristics
  +0x04 TimeDateStamp
  +0x08 MajorVersion / MinorVersion
  +0x0C Name RVA (DLL 名字符串)
  +0x10 Base (ordinal 基数，通常为 1)
  +0x14 NumberOfFunctions
  +0x18 NumberOfNames
  +0x1C AddressOfFunctions (EAT, RVA 数组)
  +0x20 AddressOfNames (ENT, RVA 数组)
  +0x24 AddressOfNameOrdinals (序号数组)

按名称查找:
  1. 二分搜索 ENT[i]（NumberOfNames 项，按字母序排列）
  2. 命中 → AddressOfNameOrdinals[i] = EAT_index
  3. EAT[EAT_index] = func_rva
  4. 如果 func_rva 在 [export_dir_rva, export_dir_rva+export_dir_size) 范围内:
     → 这是转发导出（forwarder string），格式 "DLLNAME.FuncName" 或 "DLLNAME.#ordinal"
  5. 否则返回 image_base + func_rva
```

**二分搜索实现**（freestanding C，无 strcmp/memcmp 标准库）：
- 内联 `my_strcasecmp` 进行 DLL 内函数名比较（PE 导出表按大小写敏感排序，但安全起见做精确比较）
- ENT 条目是 RVA，需要 `image_base + RVA` 读取函数名字符串

```c
}
```

**PE32（32位解释器）DLL 策略**：

PE32 通过 x86emu32 解释执行。解释器的 CALL 拦截机制基于合成地址（0x00010000 | shim_idx）。真实 DLL 的导出函数是 64 位原生代码，32 位解释器无法直接调用。

方案：
- PE32 路径下，DLL 导入仍优先走 shim 表
- 如果 shim 未命中且 `pe_dll_resolve` 找到真实导出，将导出地址注册为 32 位 shim 的 fn64 回退
- 这要求新增一个动态 shim 注册机制（扩展 IAT 表）

**简化方案（推荐首期实现）**：PE32 路径不加载真实 DLL，只对 PE32+（64 位原生）启用真实 DLL 加载。理由：Deaicup PE 版本是 PE32+（64 位 Rust），当前唯一的 PE32 程序是 hello32.exe（仅导入 kernel32/msvcrt，全部已有 shim）。

### 2.4 递归 DLL 依赖与循环检测

DLL 自身也有导入表。`pe_dll_load` 加载 DLL 后需递归解析其导入：

```c
int pe_dll_load(const char *dll_name, u64 *out_base) {
    // 1. 检查缓存
    pe_dll_entry *cached = find_in_cache(dll_name);
    if (cached && cached->load_ok) {
        *out_base = cached->image_base;
        return 0;
    }

    // 2. 读取 DLL 文件
    u8 *data; u32 size;
    if (g_dll_reader(dll_name, &data, &size) != 0) return -1;

    // 3. pe_load_image 加载（此步骤内部会调用 resolve_imports）
    //    但 resolve_imports 又可能调用 pe_dll_load → 递归
    pe_image_info info;
    int rc = pe_load_image(data, size, &info);
    if (rc != 0) return -2;

    // 4. 缓存
    add_to_cache(dll_name, &info, ...);

    *out_base = info.image_base;
    return 0;
}
```

**循环检测**：在 `pe_dll_load` 入口设置 "正在加载" 状态：

```c
typedef enum { DLL_NONE, DLL_LOADING, DLL_LOADED } dll_state;

typedef struct {
    char name[64];
    u64  image_base;
    dll_state state;     // ← 新增
    // ...
} pe_dll_entry;
```

当递归遇到 `state == DLL_LOADING` 时，说明检测到循环依赖，记日志并返回 -1（该 DLL 导入未解析，填 unimpl stub）。这是安全的降级策略。

### 2.5 转发导出（Forwarder Exports）

当 `EAT[index]` 返回的 RVA 落在导出目录范围内时，该 RVA 指向一个 ASCII 字符串，格式为 `"NTDLL.RtlAllocateHeap"` 或 `"NTDLL.#123"`。

**首期处理**：记日志，填 unimpl stub。理由：转发导出主要出现在系统 DLL 之间的内部转发（如 kernel32→ntdll），而系统 DLL 已由 shim 覆盖。真实加载的 DLL（如 Rust 编译的第三方 DLL）极少使用转发导出。

**后期扩展**：解析转发字符串，递归加载目标 DLL 并解析。

### 2.6 DLL 文件读取回调实现

DLL 文件读取回调需要从 FAT32 的 `SYSTEM/lib/` 子目录读取 DLL 文件。实现位于 `CODE/UTSM/pe/pe_dll_manager.c`：

```c

// fat32_read_path 已支持子目录遍历
extern int fat32_read_path(const char *path, u8 **out_data, u32 *out_size);

static int dll_reader_from_fat32(const char *name, u8 **out_data, u32 *out_size) {
    // 构造完整路径: "SYSTEM/lib/" + name
    // 用 fat32_read_path 读取（需支持 LFN）
    char path[128];
    // 拷贝 "SYSTEM/lib/" + name（LFN 路径）
    // 调用 fat32_read_path(path, out_data, out_size)

}
```

## Part 3: Linux 启动时 .so 推送

### 3.1 设计概览

在 Linux guest 成功 park 后、DSK 加载前，将 `SYSTEM/lib/*.so` 全部推送到 Linux guest 的 `/usr/lib/deshab/` 目录，并设置 `LD_LIBRARY_PATH`。

### 3.2 新增函数

```c

```

**实现逻辑**：

1. 确保 FAT32 block API 可用（`lxc_f32_ensure`）
2. 读取 FAT32 BPB（`f32_disk_load`）
3. 找到 `SYSTEM/lib/` 目录的簇号（遍历 `SYSTEM` → `lib`，使用 LFN）
4. 枚举该目录下所有文件（新函数 `f32_list_dir_lfn`）
5. 对每个 `.so` 文件：
   a. 读取文件内容到暂存缓冲
   b. 推送到 Linux guest `/usr/lib/deshab/<filename>`
6. 在 Linux daemon 中设置 `LD_LIBRARY_PATH`

### 3.4 内存中的文件推送

## 风险与边界情况

1. **LFN 校验和不匹配**：Windows 在创建 LFN 条目时计算短名 checksum。如果磁盘上的 LFN 条目损坏（checksum 不匹配），`fat32_lfn_process` 应标记 LFN 无效，回退到 8.3 匹配。

2. **目录跨簇 LFN 链**：LFN 链可能跨越两个簇的边界。当前的簇遍历逻辑（读一簇遍历后跟随 FAT 链读下一簇）需要确保 LFN 缓冲在跨簇时不被清空——`fat32_lfn_buf` 应在整个目录遍历期间持续存在。

3. **DLL 递归深度**：设置最大递归深度 16 层。超过后填 unimpl stub 并记日志。

4. **内存消耗**：每个加载的 DLL 使用 `kmem_alloc_aligned` 分配 SizeOfImage 字节（arena 分配器，不释放）。需在 `g_dll_cache` 中限制最大加载数量（32 个）。

5. **PE32 路径 DLL 限制**：32 位解释器不能调用 64 位 DLL 代码。首期 PE32 路径禁用真实 DLL 加载。如果未来需要 32 位 DLL 支持，需为 x86emu32 增加一个"跳板"机制。

6. **大 .so 文件**：`libstd-6g.so` 可能超过 10MB。流式推送方案必须实现，不能用 256KB 缓冲。IPC payload pool 约 1MB，分块推送即可。

7. **SYSTEM/lib/ 为空**：目录可能不存在或为空。所有逻辑必须容忍此情况，记日志但不报错。

8. **LFN 路径中大小写**：FAT32 LFN 是大小写保留但查找不区分大小写。`fat32_lfn_match` 应做大小写不敏感比较（仅 ASCII 范围）。

9. **DLL 名大小写**：PE import 中的 DLL 名大小写不敏感（如 `USER32.dll` 和 `user32.dll` 等价）。`pe_dll_load` 的缓存查找需做大小写不敏感匹配。

10. **FUCK 配置缺失**：没有 [compat] 区时所有默认值生效，行为与无配置时一致。
